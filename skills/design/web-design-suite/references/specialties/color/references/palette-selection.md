# De una paleta de referencia a un sistema utilizable

## Contexto antes de color

Reutiliza marca, tokens, colores de producto, assets y preferencias del usuario. Aclara
solo lo decisivo: propósito, tono, restricciones de identidad o tema solicitado. Evita
asociar universalmente una emoción o sector a un color; cultura, contenido y composición
cambian la interpretación. No fuerza tonos nuevos si el problema es una pareja ilegible.

Para un sistema nuevo distingue landing, producto operativo, comercio, contenido o
visualización de datos. Un dashboard denso necesita jerarquía estable; una campaña puede
usar más expresividad. Elige superficie y texto antes de distribuir acentos.

## Usar Color Hunt y otras referencias

Busca por dirección relevante: cálida/fría, pastel, oscura, natural, etc. Abre la paleta
específica y registra URL/fecha/HEX realmente obtenidos. Si no puede extraerlos, pide
los valores necesarios o propone una paleta propia identificada como tal; no atribuye
colores inventados a Color Hunt. Popularidad/likes no demuestran contraste ni adecuación.

Ejemplo consultado:
[Color Hunt: #222831 #393E46 #00ADB5 #EEEEEE](https://colorhunt.co/palette/222831393e4600adb5eeeeee).
Es materia prima; no determina automáticamente cuál sirve como texto o fondo.
Prueba por ejemplo el texto blanco sobre el teal antes de usarlo en un CTA. Si falla,
usa variante más oscura, otro on-color o limita el color original a usos adecuados.
No necesita que todas las parejas de colores de la paleta contrasten entre sí: verifica
las parejas y significados que sí aparecen en el diseño.

No copia sitios/assets de terceros ni los presenta como propios. Registra originales y
derivaciones separadas. La paleta de ejemplo incluida usa variantes propias para roles
y estados; no pretende que esos tonos adicionales estén publicados por Color Hunt.

## Roles y jerarquía

| Rol | Decisión |
|---|---|
| Fondo/superficies | Jerarquía de niveles y lectura prolongada |
| Texto principal/secundario | Contraste suficiente en cada superficie utilizada |
| Acción/on-action | CTA y contenido del botón, incluido hover/active |
| Enlace | Legible y distinguible sin depender solo de tono |
| Borde funcional/focus | Identificación del control y foco visible |
| Error/success/warning/info | Convención contextual con texto/icono, no solo rojo/verde |
| Decoración | Aporta identidad sin aparentar acción/estado |
| Datos | Identidad de serie estable o escala con significado |

Define pocos roles útiles sin imponer un número fijo de colores. Evita usar error como
acento neutro si crea ambigüedad. Las proporciones 60/30/10 pueden orientar composición,
no son una norma de accesibilidad ni obligación literal de superficie/píxeles.

Construye una escala solo cuando hacen falta estados/niveles. OKLCH puede ayudar a
controlar luz/croma/hue; pasos numéricos no garantizan contraste, gamut ni igualdad
percibida en todas las condiciones. Comprueba colores finales y compatibilidad.

## Temas y elección final

Claro/oscuro no son una inversión matemática. Reasigna superficie/texto/acento con
legibilidad y jerarquía equivalentes; conserva significado de estados y categorías.
Respeta si el proyecto solicita solo un tema. Una elección explícita del usuario debe
prevalecer sobre preferencia del sistema cuando existe selector.

Presenta opciones solo si hay una decisión abierta; recomienda una con razones ligadas
al producto. Entrega roles, valores y usos, no un listado de HEX sin instrucciones.
Un nuevo color no autoriza rediseñar toda la página ni cambiar identidad del cliente.
